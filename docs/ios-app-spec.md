# 黑流树海 iOS 截图预测与规划规格

日期：2026-10-13，Asia/Shanghai。状态：待实现的需求与算法规格。修订：以 MAA 为主要功能和算法来源，hlsh-helper 补充未知诡秘候选，路标与羽瞰点补充交互参考；不计算节点概率，保留截图导入、加工品增益、多条路线和必经节点硬约束。

## 1 用户目标与首版范围

用户在 iPhone 或 iPad 上操作游戏，通过截图导入地图。App 以 MAA 的地图感知、加工品与资源模型、安全优先规划为主线，按 hlsh-helper 的规则输出未知诡秘候选，并结合行动力、目标与加工品推荐路线。首版不需要概率统计训练数据，不计算节点概率、不按候选数量分配百分比；路线采用已确认类型收益、固定探索偏好和保守战斗代价。

首版支持 iOS 17.0、iPadOS 17.0 及更新版本，中文客户端，第一至第五层。产品不包含 macOS 客户端。

必须交付：

- PhotosPicker 和文件导入 PNG、JPEG、WebP 的单张截图。
- 地图截图、背包/加工品详情截图和移动预览截图分入口导入；识别加工品名称、剩余次数与可见效果，提交前人工确认。
- 调整裁剪区域；确认楼层、初始出生点、当前位置、出口和行动力。
- 固定拓扑模板识别、人工选择模板及手动修正节点和道路。
- 按 hlsh-helper 输出未知诡秘候选、距离与数量排除依据；未知凶戾保留待揭示状态，不扩展自编候选预测。
- 完整原始地图信息满足条件时的全局配额约束。
- 候选列表保持源分类顺序，解释缺失、冲突和全图约束降级；单候选仍标为按当前规则唯一。
- 最多 8 个必经节点、可选收益目标、行动力与确定性加工品参与的规划。
- 最多三条具有实际差异的推荐路线：综合收益、节省加工品、较低战斗风险；每条均满足同一组必经节点。
- 每步成本与假设说明；人工揭示、完成或纠错后重新计算。
- 保存本地会话、撤销最近修改，恢复最近有效地图与路线。

本轮不开发：节点概率估算及百分比显示、实时录屏、后台识别、PiP 小窗、分享扩展、云端识别、账号同步、自动操作游戏、训练模型、随机落点加工品、多层联合最优规划、第六层和树洞自动识别。

分享扩展属于后续导入便利功能。首版通过 App 内选图和文件导入即可完成闭环，不能以分享扩展或实时功能尚未实现为由延后预测与规划。

## 2 技术与实现原则

- Swift 6 语言模式，编译器 6.2 或更新；SwiftUI、Observation、Vision、Core Image、Core ML、Accelerate、PhotosUI、UniformTypeIdentifiers。
- 独立 Swift Package：TreeSeaCore，只依赖 Foundation，不直接依赖 UIKit、Vision、OpenCV 或其他参考项目。
- App UI 与会话状态由 MainActor 管理；纯数据采用 struct、enum、Codable、显式 Sendable。
- CPU 较重的识别、搜索采用明确的后台执行入口；不能把 async 当成脱离主线程的保证。采用 write-swift 技能的并发约定，优先单次操作对应单个任务。
- 核心模块不使用 MainActor 默认隔离；UI 模块采用 MainActor 默认隔离。取消、版本校验和结果提交必须明确。
- 首版不引入 App 内 Python 运行时、浏览器 WASM 或 MAA 整库；优先移植需求对应模块与资源。MAA 已公开的道路模型须经转换、来源记录与输出对照后才能启用，未通过时人工确认道路。
- JSON 保存单局会话，原子替换文件；不引入数据库、远程配置、用户可编程策略等额外机制。
- 所有性能数字是设计目标；只有设备测试后才可记录为达到。

### 2.1 前端设计与双设备要求

视觉以 [四张截图参考版 UI 规划 V2](ui-design-reference-v2.md) 为准，采用仅暗色的异色自然史拼贴、黑墨承托、版画母题和多色光域胶囊；[UI 设计规范](ui-design-spec.md) 补充有效的导航、组件反馈、业务状态和无障碍要求。V2 覆盖旧规范的色彩、展示标题、面板外形和装饰。前端实现须与算法、资源和截图导入一起交付，不能仅用静态效果图代替原生页面。

iPhone 与 iPad 共用会话和业务组件，按当前容器扣除安全区及页面左右内边距后的可用内容宽适配：Compact 或宽 <680 pt 为单栏，Regular 宽 680–959 pt 为双栏，>=960 pt 为三栏；辅助功能字号降为单栏滚动。旋转、分屏和窗口缩放保留所选节点/路线、地图视口、滚动及未提交输入，键盘不能遮挡确认/取消。

功能文字为实时系统文本并支持 Dynamic Type；点击区至少 44×44 pt、主要操作默认高 52 pt；正文对比度至少 4.5:1，必要控件边界/大文本至少 3:1。VoiceOver、触摸/指针/键盘、减少动态效果/透明度与灰度下均需有可用反馈。主题装饰不能遮挡数据或被误认为道路；地图提供节点列表替代操作。完整页面、视觉参数、分栏规则和验收任务见开发计划第 0.1 节与任务 1A、8、9、10。

### 2.2 原版图标与自建素材

游戏专有加工品、道具、节点、区域、路径和标记使用 [路标工具](https://www.lubiao.wiki/tools/blackstream-route) 的对应原版图形。原始文件位于项目根 [图标](../图标/README.md)，图集矩形、别名与 12 种移动加工品配对见 manifest；不 AI 生成、重绘、换色或用通用符号替代。展示资源与 MAA 识别模板分别记录，原版区域背景不能误称区域图标。

[自建素材](../自建素材/README.md) 仅用于背景、应用身份和与游戏对象无关的通用 UI。遵循 V2 与本地 ui参考图，包含动物骨骼版画、奔跑剪影、紫蓝墨迹和赭金细线；动物只作装饰，不代表游戏实体。iPad 封面选动物＋植物合并 v3，App 图标选首次三瓣徽记 v1。尺寸、透明通道、提示词与校验值有清单；裁切、可读性和资源占用仍须设备验收。素材缺失保留文字说明，禁止创造假原版图标。

### 3.4 无数据时如何开发

- 核心算法与测试可以使用独立设计的合成地图，不需要训练集。
- 运行时规则和模板必须逐项记录独立核对依据或明确授权。只看到仓库数值不能将 validationStatus 写成 verified。
- 原始资料不确定时保留候选，或标记需要人工确认。候选集合没有概率或置信度字段；未经核对的规则不写成游戏实测事实。
- 地图识别需要少量合法取得的实战截图做回放验收。这不是概率统计训练数据，不能用合成图的通过率代替实战成绩。
- 首版不要求一次录入 43 张模板：先对每层至少一张独立核对的模板完成实战闭环，再扩充；其余构造允许人工建立地图，界面明确自动识别支持范围。
- 未完成数据核对不会阻碍手动地图、合成用例、规则引擎和规划器开发；对应自动能力不可冒充已验收。

## 4 地图与会话状态

采用 NodeID = Int，在一层内按 row * columns + column 固定编号；楼层和会话 ID 在外层隔离。节点坐标采用 row、column，截图坐标单独保存。主层最大 50 格，核心最多接受 64 个节点以使用 UInt64 位集合；更大输入返回不支持，不截断。

FloorMap 包含：

| 字段 | 语义 |
|---|---|
| floor、rows、columns、templateID | 楼层、网格与已确认模板；自建地图允许 templateID 为空 |
| initialStartID、currentNodeID | 初始出生点与当前位置，修改当前位置不改变预测距离源 |
| exitIDs | 用户确认的终点集合；未确认时禁止给出保证到出口的路线 |
| nodes、edges | 节点与无向边 |
| originalCoverage | complete 或 partial，描述原始生成节点信息是否完整 |
| topologyVerified | 道路是否完整且通过确认，决定能否执行强距离排除 |
| mapRevision | 任意具有语义的地图修改递增 |

MapNode 包含 observedKind、originalKind、hiddenCategory、progress、traversability、identityEvidence、traversalEvidence、rewardClaimed、battleScope。原始类型在节点完成变空后仍保留；unknown originalKind 不得用当前空地代替。battleScope 默认 unconfirmed，只有用户明确确认普通战斗范围后可设 ordinaryConfirmed；不由未知凶戾图标或候选规则自动填入。

Evidence 区分 userConfirmed、directObservation、templateInferred、ruleInferred、unresolved。高匹配分不是 userConfirmed；按规则只剩一个候选也不是已揭示。

边区分 confirmed、inferred、absent。徒步步骤使用 confirmed 边；推断道路仅给待确认提示。加工品移动按射程和合法目标判断，不要求落点之间存在道路，不把飞行轨迹写回原始拓扑。

RunResources 包含 actionPoints、可选已确认 hope/ingots、加工品实例与剩余次数、costOverrides。相同名称的两件物品不等于一件有双倍初始次数的物品。用户修改库存或资源递增 resourceRevision，修改实际成本递增 costRevision。希望/源石锭总额未知时只显示已确认本次增益，不伪造初始总额。

PredictionResult 携带唯一 predictionID、mapRevision 和 ruleVersion。RouteSetResult 另外携带 resourceRevision、costRevision、goalRevision、movementCatalogVersion 和 scoreProfileVersion。任一依赖不一致时拒绝显示为当前结果。相同输入不得因异步完成顺序产生旧结果覆盖；修改收益偏好不改变候选集合。

## 5 截图导入与识别

### 5.1 交互流程

选择图片 → 校正旋转与裁剪 → 人工确认楼层 → 识别网格与模板候选 → 预览节点映射 → 确认出生点、当前位置、出口、行动力 → 提交地图 → 预测与规划。

取消、无法解码、裁剪失败、低置信度或用户拒绝提交，均保留旧会话；不删除旧有效路线。新结果未确认前作为独立预览，不直接修改当前会话。

### 5.2 首版视觉实现

ImagePreprocessor 先用 Image I/O 读取尺寸与 EXIF 元数据，限制输入文件 <=20 MiB、原图 <=1600 万像素，再通过缩略图解码应用方向，保存原图到工作图的可逆坐标变换，最长边缩放到 1280。不先解码完整大图后才缩放；超限提示先裁剪，保留旧会话。仅存需要的图片副本，截图不上传。

主要识别流程对照 MAA：归一化和地图 ROI → 网格重建 → 节点文字/图标 → 道路观测 → 已识别边与模板兼容性 → 出口身份补充 → 人工确认。完整游戏画面在去留边并确认有效画布后可映射到 MAA 的 1280×720 逻辑坐标；仅含地图的裁剪图保持比例并重新拟合网格，不强行拉伸成 16:9。固定像素 ROI 不直接套用原始 iPhone/iPad 图片。

用 Vision 中文行 OCR 适配 MAA 的文字归并和类型词典，用 Core Image/Accelerate 实现必要的图像处理和图标匹配。hlsh-helper 的占用格匹配补充模板候选，人工模板/地图为保底；不能仅凭图标未命中判断为空地，也不能将一个模板中的全部道路视为实际识别结果。

道路识别优先评估 MAA 已公开 BlackFlow_corridor_net.onnx 的等价 Core ML 导出。模型输入按配套 runtime JSON 为 RGB、Float32、3×40×160；颜色归一化按 scale=1/255、mean=0.5、std=0.25。走廊裁剪参数、原始 logit 阈值 2.2421875 与源实现对齐；导出模型须以相同走廊输入对照 ONNX 输出，记录模型及配置哈希。未通过转换或对照前，不标自动道路识别已完成，人工确认道路仍是保底入口。道路模型分数用于有边/无边判断，不输出未知节点类型百分比。

对照 MAA 的 confirmed/inferred/absent 边状态与连通性修补机制。为连通性保留的弱边依然是 inferred；界面提示待确认，不因整图连通就升级为 confirmed。

GridFitter 枚举所选层的固定行列数，计算等间距轴与平移、缩放；不处理相机拍屏的透视畸变。布局初始参考：

| 层 | 列 × 行 |
|---|---|
| I | 5 × 3 |
| II | 5 × 4 |
| III | 7 × 5 |
| IV | 8 × 5 |
| V | 10 × 5；9 × 5 只有独立模板核对后才启用 |

TemplateMatcher 优先对照 MAA：当前观测到的非 absent 边必须是模板边的子集，仅唯一兼容模板可提出出口补充，并且只给已有识别坐标的节点补身份，不新增未识别移动目标。多模板兼容时放弃自动补充。必要时使用 hlsh-helper 的占用格评分生成待人工选择的模板候选；下面的分数只属于该补充路径，不是 MAA 默认算法或正确概率：

    layout = 0.38 * recall + 0.54 * precision + 0.08 * countScore
    countScore = exp(-abs(observedCount-templateCount) / max(2, 0.30*templateCount))
    confidence = bestLayout * (0.82 + 0.18 * clamp(margin/0.12, 0, 1))

初始阈值 confidence >= 0.75 且 margin >= 0.025；这些是 hlsh-helper 的参照值，移到不同检测器后必须回放复核。只有一个模板候选时，定义 margin = 0.12，并仍执行全图覆盖、坐标残差和结构校验；不能因只装了一张模板就跳过拒识。

模板只提供推断的道路与出口。预览确认后才能成为用户确认的拓扑；OCR 冲突、缺格、多格及出口冲突不自动覆盖。

### 5.3 加工品与实际移动成本识别

地图画面不一定显示全部库存。提供导入背包、导入加工品详情、导入移动预览三个明确用途，复用图片方向、裁剪和缩略图处理。默认一次解析单张图，可将多次导入的提案确认后加入同一会话。

识别流程：用户裁剪相关面板 → Vision OCR 名称/数值/效果文本 → 与 MovementCatalog 的名称和别名匹配 → 对槽位、实例与剩余次数给出提案 → 用户确认 → 更新库存并重规划。

OCR 识别的持有件数、某实例剩余使用次数、目录初始次数、当前装载移动方式分别记录，不可混为一个数。模糊 1/7、重复图、未显示次数、两件同名物品及仅图标无文字均需人工确认；未见物品不意味着库存为 0。部分截图只更新确认覆盖的实例，不清空未显示库存。

相同截图摘要不能重复增加库存。不同截图含重叠槽位时仅在实例匹配唯一且证据充分时更新；无法区分两件同名物品则要求选择原实例或新增实例，不按名称自动累加。完整库存替换必须由用户明确确认覆盖范围。

实际移动预览截图可识别徒步/加工品方式、目标和 AP 消耗；只有用户确认目标与方式后才写入该动作的成本覆盖。不能把某一次实际成本泛化给所有加工品或所有目标。

参考 MAA 的当前装载方式模板、库存格定位及预览成本 OCR，但不照搬 Win32 坐标或自动点击。其固定提交的装载识别明确缺少 M04/M12 图标任务，因此不能宣称该项目已经提供完整十二种背包识别。首版以名称/详情 OCR 与手动录入为保底；图标识别只在合法样例与回放通过后启用。

## 6 未知节点预测规则

### 6.1 规则类型与结果语义

DistanceRule：forbidden、unrestricted、closedRange(min,max)。研究资料中的 null 映射 forbidden，undetermined 映射 unrestricted，闭区间含端点。缺少条目与 forbidden 是不同状态：缺少时不执行该条排除。

CountRule：closedRange(min,max) 或 allowedTotals(Set<Int>)。研究资料中的 null 表示该层数量 0；缺失条目表示未核对。离散数量如 0 或 2 不得展开成 0...2。

NodeRule 保存 typeID、hiddenCategory、各层距离与数量规则、sourceURL、sourceRevision、validationStatus、distanceMetric。运行时强规则必须经过独立核对或授权后的数据审查；否则结果保留 needsRuleReview 提示。

PredictionResult 输出 candidates、exclusions、warnings、propagationStatus、predictionID、mapRevision 和 ruleVersion。candidates 是按源分类顺序排列的类型列表，不带概率、出现权重或似然排名；exclusions 保存排除原因。视觉模板匹配分只用于识别提案，不进入候选列表。

### 6.2 距离定义

在用户确认的原始拓扑上，以 initialStartID 为源进行无向等权 BFS，起点距离 0，每条模板边长度 1。不使用曼哈顿距离，不使用当前位置，不经过加工品的飞行边，也不对险路尽头额外补边。

如果原始拓扑不完整、出生点不确定或规则距离版本不相容，跳过距离排除，显示原因。断开的节点距离未知，不凭无穷距离排除全部类型。

### 6.3 类别

unknownMystery 初始 11 种候选：诡意行商、秘境行商、安全的角落、不期而遇、得偿所愿、失与得、先行一步、误入奇境、狭路相逢、应急助力、险路小径。

固定提交的分类表只有 unknown_mystery。unknownFerocity 不运行候选筛选、不生成作战/紧急作战候选列表，显示待揭示；居民预测及标记推断不纳入本轮候选模块。路线若需经过未知凶戾，必须由用户确认它属于普通战斗范围，否则要求先揭示；这是规划模型的资格确认，不能写成 hlsh-helper 的类型预测。

### 6.4 独立筛选

对未知节点 v 和同类别类型 t：

1. 距离规则 forbidden：排除；closedRange：只有可靠距离越界才排除；unrestricted：保留。
2. 统计可信的 originalKind 已揭示数量 K_t，包含完成后变空的原始节点，排除不可靠识别。
3. 若已核对的最大数量 U_t 已达到，即 K_t >= U_t，按源实现排除 t；数量上限缺失则不执行这条排除。
4. 每次排除保留 reason，包括距离、规则区间、已出现数量、上限和来源版本。

如果 K_t > U_t，记录数量冲突，不进行全局配额传播，返回源独立筛选结果并提示复核识别和规则。局部筛选仍遵循 K_t >= U_t 的上限条件；不得为维持非空列表把已排除类型填回。整体流无解的回退同样是独立筛选结果，不能承诺该列表必然非空。

### 6.5 全局配额传播

启用前必须全部满足：

- 原始节点覆盖完整，所有相关未知原始节点均在候选变量集合内。
- 初始拓扑、出生点和类别已确认。
- 使用的类型数量规则已核对且没有已知数量超限。
- 原始类型未知的已完成节点没有遗漏；若有遗漏，禁用最小配额传播。

对每种类型：

    residualMin = max(0, totalMin - knownOriginalCount)
    residualMax = totalMax - knownOriginalCount

每个未知诡秘必须恰好赋一个候选类型。建立源点→未知节点→类型→汇点的带上下界流，添加汇点到源点的循环边，并通过超级源/汇满足节点流量平衡；按 hlsh-helper 移植 Dinic 判断可行性。

离散总数规则枚举允许总数的组合，任意组合可行即保留。首版 11 类参照表本身没有离散总数，但通用解析不能把资料中的离散约束改成范围。

先检查整体可行。再逐个固定候选 v=t，检查是否存在一个完整赋值；全部组合不可能才剔除，保留原候选顺序。这一阶段只判断可行性，不统计合法赋值占比，不计算概率。

整个候选预测预算：100 ms 和 1000 次候选可行性检查，包含输入检查、BFS、局部筛选、整体可行检查、离散枚举和逐候选固定。独立筛选已完成后全图预算耗尽，返回本轮独立候选、propagationStatus=incomplete，不能用只完成一部分检查的结果继续传播；独立筛选也未完成时返回未完成状态，不拼接残缺列表或冒用旧图结果。取消不提交。

整体无解返回独立候选与 conflict，不把全图删空。截图不完整返回 skippedIncompleteCoverage。人工确认节点后，更新 originalKind、已出现数量和未知集合，全量重算。

### 6.7 候选显示与局限

候选模块以 hlsh-helper 的 [分类表](https://github.com/ega0123/hlsh-helper/blob/b81965ba78918d8d6effb0e5006dc3c9b2e617c9/data/rules/node_categories.json)、距离表、数量表和 candidate_filter.py 为基准。对已核对、覆盖完整且无冲突的输入，Swift 与源实现应输出相同集合及相同顺序；对应校验使用固定提交的结果，不追随浮动 main。

- 界面只显示可能类型列表、出生点距离、排除原因和全图约束状态。分类顺序是展示顺序，不代表出现倾向。

- 缺失规则或部分原始地图时，跳过不适用约束并解释；无解时回退独立筛选列表。空列表显示当前规则无可用候选并要求复核，不自动补全。
- 原始身份、出生点或拓扑误识别仍会影响候选，规则本身也可能过时。唯一候选不等于识别正确或游戏已确认。
- 修改收益权重、加工品或必经条件不改变候选；揭示原始节点或修改地图/规则后，重新筛选和传播，再规划。
- 全部候选运算共享 100 ms、1000 次可行性检查预算，涵盖输入检查、BFS、局部筛选与全图传播；取消不提交，超时按第 6.5 节处理并标记未完成。这是本 App 的执行边界，不是源项目的性能承诺。

## 7 路线规划算法

### 7.1 首版目标

在用户已声明的地图、成本和资源模型内，返回最多三条满足必经节点并到达选定出口的不同路线。首次支持最多 8 个无序必经节点；默认用户在地图点选，按节点位置定义，不要求身份已经揭示。节点存在及坐标必须确认，不自动将单候选未知节点当作已确认商店。

默认必经语义是实际经过：徒步 path 中确实到达的格点或加工品实际落点满足条件；飞行几何连线越过某格不算。当前所在节点若被选择视为本轮已满足，过去曾完成但本轮未经过的节点仍需重新到达。已完成空地和普通未知内容节点均可选；未建模特殊节点仍要求先揭示。若另有必须进入内容或类型为商店的条件，必须显式确认该语义和资格，不能用经过位置偷换。

所有推荐采用同一组必经约束，不为了多给路线降低条件。用户取消或改变必经节点递增 goalRevision。首版不支持指定访问顺序或八个以上必经节点。

路线按第 7.5 节的固定权重、已确认资源和保守战斗代价评分；不计算未知类型的期望收益。安全说明只保证所声明的移动与行动力模型，不保证战斗必胜或未知事件没有副作用。

### 7.2 状态

PlannerState = (position, AP, completedMask, openedMask, rewardClaimedMask, mandatoryGoalMask, itemCharges, confirmedResourceDeltas)。

UInt64 位集合分别保留已完成、已打开与已领奖信息；三者不能无条件互相替代。图、规则与 PredictionResult 在一次搜索中不可变；动作实际成本覆盖由请求快照提供。候选结果修订或规则版本改变也会使旧路线失效。

动作包括：

- walk：沿 confirmed 道路穿过 empty、已打开或已确认可通行节点。未进入的内容节点挡住继续穿行，BFS 到该节点后停止该分支扩展。BFS 状态保存 (格点, 本动作经过的必经位集合)，不能只保留同目的地的一条不含必经点的最短路径；所有真实 path 格点更新 mandatoryGoalMask。
- deterministicItem：使用用户已核对或人工录入的确定性加工品。射程可为正交 2 格、周围 8 格、曼哈顿 2 格、正交 3 格、全图，另带目标白名单与次数。

只保存当前输入中实际持有且用户确认的加工品实例，使用第 5.4 节的参照目录与核对后的值。若两件标准引擎剩余次数为 1 和 3，预算是 4 次，不是目录初始 3 次，也不是按两件自动填成 6 次。状态逐实例扣次数，界面说明具体使用哪件。未知增益或未确认射程不能加入可执行动作。

随机落点、传送配对未知、自动改变地图的特殊节点，首版不给确定路线；需手动揭示或选择其他目标。

### 7.3 成本、增益与状态转移

徒步默认按每条边 1 AP 估计；这是第一版的模型默认值，不在未经实战核对时声称游戏成本恒定。预览确认的 actionCostOverrides 优先。未确认成本计入 assumptions，使结果显示按当前估计可执行。

先判断当前状态是否已经到达终局；非终局动作检查 AP >= max(minimumAPToStart, cost)。默认 minimumAPToStart=1，即使 cost=0 也不能凭空在 AP=0 时启动。随后原子应用：

    nextAP = AP - cost + confirmedItemAPGain + confirmedNodeAPGain
    nextItemCharge = itemCharge - 1   // 仅加工品动作
    nextHopeDelta = hopeDelta + confirmedItemHopeGain
    nextIngotDelta = ingotDelta + confirmedItemIngotGain

只有核对且确认的加工品效果和一次性节点收益进入资源转移；未知事件、安全角落和未确认羽瞰收益默认 0。简易遥控器每实际使用一次增加 3 AP，同时扣该实例一次；不是无次数限制的免费充能。初始 AP=1、cost=0、确认增益 3 时结果 AP=4；AP=0 时默认不能启动。MAA 存在一次羽瞰 +1 的模型，但独立核对前不启用该增益，确认后同一羽瞰节点最多计一次。

希望与源石锭的确定增益记录到每步与累计资源摘要；首版不模拟未来购物、加工、随机获得新道具或消耗希望招募。资源来自实际模拟动作，只能在搜索快照中增加；用户执行前不修改真实库存。

节点完成、阻挡解除、是否可重复必须有明确定义。未知内容完成后是否可穿行尚未确认时，其后续路径属于 assumption，不显示为确认安全。重复访问同一商店、羽瞰点或休息点不得重复发放奖励。实际揭示有不同结果时更新会话再规划。

到达选定出口且 mandatoryGoalMask 完成即终止，允许 AP=0；出口不作为本轮中间穿越点。预测距离仍按第 6 节计算，两种语义独立。

### 7.4 搜索

以 MAA SafetyValue 与 Planner 为主要移植对象：先在当前动作、资源和终局模型中判断安全可达，再做收益搜索。首版只启用确定性动作，因此移植其确定性子集的记忆化、资源支配和可达性检查；随机动作仍不启用，不宣称已经覆盖完整 AND-OR 随机安全 oracle。

SafetySolver.check(state:snapshot:control:) 输出 reachable、unreachable 或 unresolved，并携带可证明时的 minimumRequiredAP。终局同时检查出口和全部必经位；原 MAA 终局需适配这一要求。增益动作和循环必须采用源实现的有界预算状态/固定点处理，不能把递归中的临时未完成状态当成无解；超时返回 unresolved。安全阶段、收益搜索和多路线选择共享同一 300 ms 截止时间，不能照搬 MAA 在安全检查完成后才启动收益时限的计时边界。

步骤：

1. 检查出口、当前位置、必到目标、资源与成本资料有效性。
2. 对照 MAA 动作与状态生成，在共享预算内做确定性安全/可行性检查，并用贪心完整路径给收益搜索提供首个 incumbent；安全未完成不能写成无解。
3. 移植 MAA 的 best-first 标签、资源支配和收益上界剪枝，再以三种偏好与多样性保留策略收集完整路线，三种偏好见第 7.4.1 节。
4. 每次展开检查实际可支付成本，更新状态、收益与资源。
5. 标签保留 mode、路线前缀与资源状态。只有相同偏好、状态语义与相同多样性类别内使用支配剪枝；不同加工品安排和必经进度不能只按单条最高分删除。每个状态/偏好最多保留三种不同有意义的前缀，受全局标签上限约束。非证明性的前缀裁剪记录 heuristicLimited，不能视为穷尽全部可能。
6. 综合收益上界包含所有未领奖已揭示节点的非负收益、未知诡秘固定探索分、可靠羽瞰信息收益及剩余加工品可能带来的确定希望/源石锭收益；未知候选类型的收益不计入。其他偏好用各自可证明的界。候选池未满时不得只用第一条 incumbent 提前剪掉全部备选；使用相应偏好的最差保留候选作阈值。
7. 返回 RouteSetResult：0–3 条唯一推荐、每条步骤/资源/必经覆盖/评分/假设，以及共享的预算和依赖版本。不称全局前三最优。

禁止用纯徒步距出口的 AP 当硬剪枝：羽瞰增益和飞行可能使其错误排除可行路线。可用于排序；用于证明的下界必须可证明不高估，否则取 0。

首版预算：整个 plan 调用 300 ms、最多 20,000 次状态展开、最多 40,000 个保留标签。三种偏好共享此预算，不各自运行 300 ms。计时从输入检查前开始，覆盖可行性搜索、必经 BFS、动作生成、三种偏好搜索、去重与选择。先用至多 60 ms 寻找首条可行路线，即使该阶段未找到，后续队列仍继续寻找；剩余时间按偏好轮转分配，某偏好耗尽队列时将余量分配给其余偏好。每次展开及内部批处理至少每 32 项检查截止时间和取消。

预算耗尽且已有完整路线：返回 feasible、budgetLimited，允许只找到 1 或 2 条，不用重复路线凑数。预算耗尽且未找到：返回 unresolved，不写无解。非证明性前缀或标签裁剪导致未找到时同样返回 unresolved、heuristicLimited；只有未受这些截断且搜索穷尽、无路线时返回 noFeasibleRoute。已证明某个必经节点不可达时说明节点与已知限制，不自动删除它。取消结果不覆盖已有会话。

相同输入的并列路线按：分数高、跨层加工品消耗少、剩余 AP 多、路径边数少、节点 ID 序列字典序小。整数评分单位完全相同才视为并列，支配与上界比较同样采用整数。禁止依赖 Dictionary 遍历顺序。

### 7.4.1 三种推荐偏好与路线去重

| 偏好 | 终局比较顺序 |
|---|---|
| 综合收益 | balanced-items-v0.4 分数高，之后沿用资源/距离并列规则 |
| 节省加工品 | 跨层保留加工品消耗少 → 加工品总使用次数少 → AP 毛消耗少 → 综合分高 |
| 较低战斗风险 | 累计保守战斗代价少 → AP 毛消耗少 → 跨层加工品消耗少 → 综合分高 |

收集至多 32 条完整候选。优先每个偏好选一条，再从候选池补足最多三条。若多个偏好选择同一条，只保留一条并标注多个适用偏好；不能把同一路线改个标题当三条。

规范化路线签名包含：有序内容/必经停靠节点、出口、加工品的类型与使用源点/落点/次数。相邻徒步步骤切分方式与两个等价同名实例 ID 不构成不同推荐。至少节点路线、出口或加工品安排之一实质不同；不增加无收益绕圈制造差异。不同前缀有重访必要时允许重访，不禁止所有重复节点。

每条路线展示必经节点全部打勾、偏好分与保守战斗代价、AP 毛消耗及结束余额、加工品消耗与剩余、确定资源增益、推断/成本假设。地图用不同颜色切换查看一条路线，飞行箭头与徒步道路区别绘制。

这是本项目新增的多路线设计；MAA 提供动作候选与单次决策参考，不能宣称其已经实现本规格的三偏好推荐界面或全局 K 最优。

    routeScore = 已揭示节点首次访问收益
               + 4 * 首次访问的未知诡秘节点数
               + 可靠羽瞰信息收益
               + 已确认加工品希望增益
               + 0.5 * 已确认加工品源石锭增益

               - 0.25 * 徒步边数

               - 3 * 跨层加工品使用次数

所有权重以 0.25 分为单位存 Int；例如秘境行商 56、探索偏好 16、每条道路边代价 1、普通未知凶戾代价 32、每点希望收益 4、每枚源石锭收益 2。ScoreDelta、累计评分、支配和上界比较均用整数单位，避免引入概率计算留下的浮点分数；显示时除以 4。新增资源收益系数是初始偏好，不是经济兑换率。AP 增益通过可行性、后续可访问节点和结束余额参与，不额外加奖励。

未知诡秘的 +4 只表示愿意探索的固定偏好，不承诺有收益；即使只剩商店候选也不发放商店 +10/+14 或资源增益。节点实际揭示后按已知类型重新规划，不再加未知探索分。重复访问同一节点不重复收益或探索分，不改变真实持久化领奖状态。

算例：S-v-E 共消耗 2 AP、走 2 条边，v 为未揭示诡秘，无论有几个候选，路线分数 =4-2-0.5=1.5，即内部 6 单位；v 已揭示为诡意行商时 =10-2-0.5=7.5，即 30 单位。普通未知凶戾的保守代价为 8 分；揭示为普通作战后改为 4 分，不做混合风险估算。

必经条件是硬约束，不为了分数删除用户目标。按位置选择未知节点可要求经过该位置，但必须到已确认商店的条件必须有确认身份。首版不设置资源预留数量，不做跨层自动求解；跨层加工品保留通过使用代价和并列排序表达。

### 7.5.1 候选进入规划的边界

- 一次搜索冻结地图、候选结果、规则版本与资源，不在模拟访问时假装揭示类型或重做筛选。
- 候选列表用于解释当前不确定性和确认需求，不计算类型平均收益、加权收益或信息熵。未知诡秘探索分固定为 4；未知凶戾按用户确认的战斗范围使用保守代价。
- 未确认的 AP 增益、加工品次数、射程、目标资格或拓扑都不能从候选中推导。商店单候选不能自动满足行商加工品目标限制。
- 未知节点完成后变空与通行的效果仍须作为路径假设说明；类型未建模、空候选或冲突须先复核，不生成经过该节点的确认可执行路线。
- 规划输入验证 mapRevision、predictionID、ruleVersion、resourceRevision、costRevision、goalRevision、movementCatalogVersion 和 scoreProfileVersion；不新增概率快照或配置版本。
- UI 显示推荐路线、偏好分、已确认收益和保守战斗代价，不显示类型百分比、路线成功率或全局最优承诺。固定探索偏好可能让路线选择未知节点，但实际奖励与副作用需揭示后重规划。

### 7.6 重规划

修改类型、完成状态、位置、AP、加工品库存/次数/效果、道路、出口、必经节点、实际成本或规则/收益配置后，先失效全部旧路线，再对新快照计算。揭示原始身份后重新筛选候选和传播配额，再进行多路线规划。查看或切换推荐不扣实际次数；用户确认已执行步骤或导入新资源截图后再对账。界面可以显示最后有效路线，但必须标注已过期。

## 8 验收标准

### 8.1 规则与规划

- 人工确认出生点后，改变当前位置不改变出生点距离。
- 可靠数量达到上限时排除对应候选；已完成变空节点仍消耗原始配额。
- 截图不完整、原始类型丢失、规则缺失或冲突时不误用最小数量约束。
- 全图约束可证明的候选删除与暴力枚举小图结果一致。
- 非空独立候选不能因约束无解被全部静默删空。
- 已核对完整输入的候选集合和顺序与固定提交 hlsh-helper 一致；全图流只做可行性排除。
- MAA 加工品目录、动作几何、资源转移、安全可达与共享搜索子集通过源实现 fixture 对照；源码策略权重和 App 适配权重分别记录。
- 候选 UI 和模型没有类型百分比、出现权重和概率接口；单候选标按当前规则唯一，不标已揭示。
- 未知凶戾不生成自编候选列表；未确认普通战斗范围时要求揭示，不默默按普通战斗规划。
- 修改收益权重不改变候选；揭示节点后重算候选与配额。
- 已声明的算例得到未知诡秘路线 1.5 分、已揭示商店路线 7.5 分、普通未知凶戾保守代价 8 分；重复未知节点不重复探索分。
- 单候选不能透支 AP、确认未知商店身份或让徒步越过未确认道路；确认的加工品飞行独立按合法落点判断。
- 加工品 OCR 提案不自动成为库存；持有件数/剩余次数/初始次数不同，部分图不清空库存，重复图不增加次数。
- M12 的确认增益能改变可达性，但每次扣次数；AP=0 不因 cost=0 越过默认启动门槛。
- 必经空地和未知节点按实际 path/落点满足；飞行掠过不算，同终点的不同必经覆盖路径不能错误合并。
- 至多三条推荐都满足必经条件；重复路线合并，只有一条可行时不伪造三条；综合、节省和风险偏好可输出不同结果。
- 路线每步 AP 不为负；增益与奖励只计算一次；加工品次数不透支。
- 最终到选定出口且所有必到目标完成。
- 小规模可穷尽用例中，搜索评分与独立暴力枚举最优值一致。
- 预算耗尽、取消、无出口、未知成本与过期结果有不同状态。

### 8.2 图片与产品

- iPhone 与 iPad 实际图片导入、横竖方向、安全区、裁剪、纠错、恢复均可操作。
- 按 V2 视觉实现全部首版页面；单/双/三栏、iPad 分屏和窄窗口、辅助功能字号、键盘出现时都能操作，布局变化不丢选择、视口或编辑草稿。
- Dynamic Type、VoiceOver、触摸/指针/键盘和减少动态效果/透明度实际验收；对比度与命中区满足第 2.1 节，状态不只靠颜色表达。静态图的待生成/待审阅记录不写成设备验收通过。
- 每层至少一张独立取得实战截图完成自动或半自动闭环；未支持构造允许手动图。
- 有效图、不完整图、模糊图、节点遮挡、同分模板、带 HUD 图片分别记录回放结果。
- MAA 逻辑画布到截图的坐标变换可逆；道路模型导出有输入/输出对照，弱边连通性修补不升级为已确认。裁剪图不能直接套用完整画面 ROI。
- 目标而非实测：1280 工作图常规识别 P95 <=2 s；整次候选预测 P95 <=100 ms；默认规划预算 300 ms，取消后 P95 <=100 ms 内停止并不提交。
- 以 Instruments 测 UI 卡顿、峰值内存与重复导入；峰值内存目标 <=150 MiB，连续 20 次导入无持续增长趋势。原始解码峰值也应计入。
- 人工验收与自动测试分开。没有实战截图或真机结果时，只能标核心逻辑已验证，不能标识别实用性通过。

## 9 后续评估

完成首版后再独立调研 iOS 屏幕捕获、后台推理与 PiP。届时按 SDK 和系统版本重新核对 [ScreenCaptureKit iOS 样例](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-on-ios)与 [PiP 内容源](https://developer.apple.com/documentation/avkit/avpictureinpicturecontroller/contentsource-swift.class)，不能把当前截图架构当成后台常驻保证。
